# 공동 문제 처리 흐름 개선 — 2026-10-07

## 사용 중 발견한 문제와 결정

| 불편 | 변경한 동작 |
| --- | --- |
| 민원을 골라도 제목을 새로 작성해야 함 | 선택한 제목의 단어를 민원별 한 번씩 세어 주요 두 단어로 제목 제안. 직접 고친 제목은 유지. 숫자·동호수·일반 요청 문구 제외. AI 추천이나 개인정보 자동 제거를 보장하는 기능은 아님 |
| 묶기 후 어디서 처리해야 할지 불분명 | 생성 후 상세 처리 입력란으로 이동 |
| 공동 문제와 민원 목록 상태가 다름 | 연결 중에는 공동 문제 상태가 기준. 처리 중·완료·재개 모두 연결 민원에 같은 트랜잭션으로 반영. 개별 변경 대신 공동 문제 화면으로 안내 |
| 조회수만으로 관리자 확인 여부를 알 수 없음 | 소속 관리자의 상세 확인 시각을 별도 저장. 미확인/확인함과 처리 상태를 분리하고 미확인·미처리 필터 제공 |
| 완료 후 공지가 올라갔는지 불명확 | 완료 저장 후 공지 작성 여부 확인. 선택한 경우 공개용 설명과 완료 내역으로 초안을 열고, 최종 등록 때만 단지 전체에 게시 |
| 공지 등록 실패인데 목록으로 이동 | 오류와 작성 내용 유지 |

원본 민원 내용·공개 여부는 보존한다. 최초 연결 때 처리 중 민원이 있으면 공동 문제도 처리 중으로 시작하며 완료 민원은 새 묶음에서 제외한다. 해제한 민원은 마지막 처리 상태를 유지하고 이후 공동 문제 알림 대상에서 빠진다.

## 검증한 내용

- 분리된 PostgreSQL 16 DB에 마이그레이션 26개 적용.
- 민원 회귀 27개, 공동 문제 통합 24개, 제목 제안 3개: 총 54개 통과.
- 업무 상태·연결 민원 상태·이력·알림·Outbox의 롤백, 동시 업데이트, 작성자별 중복 방지, 단지 격리, 관리자 확인·작성자 수정 후 미확인 복귀 검증.
- 실제 Chromium에서 관리자 로그인, 미확인 표시·필터, 제목 제안·수동 수정 유지, 생성 후 상세 이동 검증.
- 브라우저에서 저장 응답을 의도적으로 유실시킨 후 재시도: 동일 requestId 사용 및 처리 이력 1건 확인.
- 브라우저 시간대를 Asia/Seoul로 설정하고 입력한 예상 처리일이 새로고침 후에도 같은 현지 시각인지 확인.
- 완료 안내를 취소하면 공지가 생성되지 않음. 초안에는 비공개 원문이 들어가지 않음. 공지 등록 503 응답에서는 입력 유지, 이후 정상 등록 201 및 목록 이동 확인.
- 주민별 공동 문제 응답에 자신의 민원만 포함되는지 확인. 브라우저 JavaScript 오류 없음.
- 최종 화면 빌드 후 같은 브라우저 흐름 재검증 완료. 검색 버튼, 개별 민원의 상태 변경 후 같은 페이지 갱신, 완료 안내에서 확인을 선택한 경우 공지 초안으로 이동하는 동작도 통과했다.
- 테스트 고유 ID·본문이 일치하는 임시 민원 18건, 공동 문제 4건, 공지 3건과 관련 DB 알림을 정리했다. 기존 민원 3건과 공동 문제 1건은 보존했고 연결 상태 불일치는 0건이었다. 검증용 PostgreSQL 컨테이너를 제거하고 데모 서비스는 실행 상태로 유지했다.

## 화면을 단순하게 유지한 범위

- 관리자 목록은 조회수·댓글 수 대신 제목·작성자·작성일·공개 여부·확인 여부·처리 상태에 집중한다.
- 색뿐 아니라 상태 글자를 표시하고, '접수전'을 '처리 대기'로 변경한다. 서버에서 지원하지 않는 '처리불가' 선택지는 제거한다.
- 입력란 이름 연결, 키보드로 조작 가능한 기본 선택 상자, 44px 이상 주요 버튼과 더 높은 글자 대비를 적용한다.
- UUID 대신 연결된 민원 제목을 표시한다. 실패 시 빈 목록이나 무한 로딩으로 오해하지 않도록 오류와 재시도를 제공한다.

## 남은 한계

- 고령 사용자 대상의 실제 사용성 조사나 서비스 전체의 접근성 인증을 수행한 것은 아니다. 이번 검증은 민원→공동 문제→처리→공지 흐름에 집중했다.
- 관리자 확인 시각은 현재 단지 관리자 1명 모델 기준이다. 여러 관리자별 읽음 기록이 아니다.
- AI 유사 민원 추천, 전체 공지와 공동 문제 사이의 영구적인 DB 연결·발행 이력 추적은 아직 없다. 공지 초안은 별도 공지 작성으로 이어지며 관리자가 발행 여부를 판단한다.
- 알림 레코드 중복 방지는 검증했지만 네트워크 전송 자체가 정확히 한 번이라는 보장은 하지 않는다.
